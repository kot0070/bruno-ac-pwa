## Executive verdict

**VERDICT: C — REJECT / REWORK REQUIRED.**

Four of the five prior P1 blockers are closed at the audited HEAD: the live engine now consumes the canonical plan rather than the `{version, plan, result}` wrapper; Confirm & Save uses the canonical room plan; canonical room-plan persistence/reload is restored including legacy-wrapper migration; and confirmed snapshot `compliance.ready` is no longer hard-coded true while `required-input` checks remain.

The prior stale-BOM/Apply blocker is **not fully closed**. The new fail-closed logic only runs when `room-estimator-live.js` receives an `input` or `change` event (or is explicitly rebuilt). Several room-estimator controls mutate the plan from `click` handlers and call the UX `render()` directly without emitting `input/change` and without calling `BrunoRoomEstimatorLive.rebuild()`. If one of those click actions changes a previously valid plan into a blocked plan, the authoritative Calculator keeps the old in-memory `scope`/`bom`, the Apply button remains enabled, and the stale BOM can still be written to the Job.

The strongest deterministic reproduction is `Clear overrides` while duct/return overrides are the values that make a new/replacement-duct plan valid. Clearing them creates room-engine blockers, but the live invalidator is never scheduled. A second deterministic path is `+ Add room` in a new/replacement-duct plan when the new conditioned room lacks a branch/run takeoff: UX becomes blocked, but the live invalidator is not scheduled. This is the same financial/product integrity class as the prior F04 and remains P1.

F06 duplicate provenance is closed. F07 import validation is improved but remains only partially closed: `customerTotal` and `yourTotal` must now be finite/present, but malformed `marginDollar` / `marginPct` are still normalized to `null` and accepted, and negative totals are accepted because `validPricing()` only checks finiteness. This is retained as P2 because imported history does not drive live Catalog pricing or Job Apply, but it still fails the task's strong malformed-historical-pricing acceptance condition.

### F04 — fail-closed stale BOM / pricing / Apply

**OPEN — P1.**

The new invalidator is correct when invoked:

- disables `#apply`;
- marks `#bomBody` stale;
- clears displayed pricing totals;
- changes calculator state/gate wording;
- preserves ownership metadata so a later valid state does not incorrectly override a pre-existing disabled state.

However invocation coverage is incomplete.

`room-estimator-live.js::init()` subscribes to:

```text
card: input, change
sqft: input, change
ductMode: change
```

It does **not** subscribe to `click`, DOM mutations, or a central plan-change event.

Meanwhile `room-estimator-ux.js` has click-only mutation paths:

```text
re-add              -> mutate plan.rooms -> render()
re-preset           -> replace plan -> loadForm()/render()
room-delete         -> mutate plan.rooms -> render()
re-clear-overrides  -> plan.overrides={} -> render()
```

When `render()` sees `result.ready === false`, it only calls `refreshPricing()`; it does not call `BrunoRoomEstimatorLive.invalidateCalculatorPreview()` and does not clear/disable the authoritative Calculator itself.

Deterministic stale-Apply reproduction from source behavior:

1. Start with `ductScope=replace` or `new` and a valid plan whose missing room takeoff / return design is resolved by explicit overrides.
2. Let live preview calculate the authoritative Calculator; `#apply` is enabled and Calculator `scope`/`bom` are current.
3. Click **Clear overrides**.
4. UX recomputes the room engine and now has `ductFt` and/or `returnGrilles` blockers.
5. No `input` or `change` event is emitted by that click handler and no explicit live rebuild is called.
6. `room-estimator-live.js` therefore does not run `invalidateCalculatorPreview()`.
7. The old Calculator `scope`/`bom` remains in memory and `#apply` remains enabled.
8. Clicking Apply executes `ac-calculator.js::applyToJob()` against that stale BOM and can write stale generated materials to the Job.

A second path exists with **+ Add room** in new/replacement duct scope when the added conditioned room has no branch/run takeoff: the UX becomes blocked, but the click-only mutation does not schedule the live invalidator.

This violates the explicit acceptance gate: **blocked live state must be fail-closed and old BOM cannot remain Apply-able**.

## F06 / F07 re-check

### F06 — duplicate provenance

**CLOSED.**

`duplicateForEdit()` returns the source snapshot ID. `calculation-history-ux.js::duplicate()` stores it in `pendingSourceCalculationId`; `currentSnapshot()` includes that field; successful save clears the pending value. History rendering displays `duplicated from <id>`.

### F07 — malformed / missing historical pricing

**PARTIALLY OPEN — P2.**

The fix correctly rejects missing/malformed `customerTotal` and `yourTotal` values that normalize to `null`.

But `validPricing()` is only:

```js
numOrNull(p.customerTotal)!==null && numOrNull(p.yourTotal)!==null
```

Consequences:

- `marginDollar:'bad'` is normalized to `null` and the snapshot is still accepted/imported;
- `marginPct:'bad'` is normalized to `null` and the snapshot is still accepted/imported;
- negative `customerTotal` / `yourTotal` values are finite and therefore accepted, despite the accepted financial semantics treating negative financial values as invalid.

Example accepted payload shape:

```json
{
  "pricing": {
    "customerTotal": 100,
    "yourTotal": 70,
    "marginDollar": "bad",
    "marginPct": "bad"
  }
}
```

The imported record can then appear as an active frozen historical snapshot with incomplete/misleading pricing metadata. It does not feed live Catalog repricing or Job Apply, so this remains P2 rather than P1, but the task's strong import requirement is not fully met.

3. Strengthen imported historical pricing validation so malformed or semantically invalid financial snapshot fields are rejected/skipped rather than normalized into an admitted record. At minimum cover malformed margin fields and negative totals consistently with accepted financial semantics.
