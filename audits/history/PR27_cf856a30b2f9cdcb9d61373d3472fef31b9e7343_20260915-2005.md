## FINDINGS

### F01 — P1 — Journal schema v4 stable-worker restore validation is incomplete

TASK_CURRENT requires, before any restore write:

```text
Journal JSON parses
supported schema/version enforced
settings/calls/crew shape validated
schema 4 stable-worker shape validated
malformed/unsupported payload fails closed
```

Current `app-backup-bridge.js` validates:

- Journal object;
- schema version 3 or 4;
- `settings` object;
- `calls` array with call `id` and `date` strings;
- `crew` array with crew `id` and `date` strings;
- for schema 4: `workers` is merely an array and each crew row merely has a string `workerId`.

It does **not** validate the schema-4 stable-worker structure itself. For example, payloads structurally equivalent to these can pass the current `validateJournalRaw()` boundary:

```json
{"schemaVersion":4,"settings":{},"workers":[null],"calls":[],"crew":[]}
```

or a crew row can reference a `workerId` that does not exist in `workers`.

The current backup test confirms rejection of malformed JSON and unsupported schema, but it does not exercise malformed worker records, duplicate/empty worker IDs, or dangling crew `workerId` references.

This leaves F02 only partially corrected: restore is atomic with respect to validation, but the required schema-4 identity shape is not actually enforced before writes.

Required correction:

- validate each worker as an object;
- require non-empty stable `id` and expected `name` shape;
- reject malformed worker arrays;
- reject missing/invalid schema-4 crew worker IDs;
- preferably require every schema-4 crew `workerId` to resolve to a worker record;
- add negative tests proving restore writes do not occur for each malformed worker-shape fixture.

### F02 — P1 — Commercial → Residential bridge can incorrectly enable Apply

`project-mode-bridge.js` owns a visual/interaction guard. In Commercial it sets:

```text
applyBtn.dataset.commercialBlocked = '1'
applyBtn.disabled = true
```

When Residential is restored, it does:

```text
if(applyBtn && applyBtn.dataset.commercialBlocked) {
  delete applyBtn.dataset.commercialBlocked;
  applyBtn.disabled = false;
  applyBtn.title = '';
}
```

This unconditional `disabled=false` does not recompute the calculator's other gating conditions.

The wizard's type-change path recalculates first and can correctly disable Apply because:

- project plan is still not ready; or
- calculator BOM has unresolved items; or
- calculator BOM has invalid financial data.

But `project-mode-bridge.js` separately handles the same change event with a deferred `scan()`. On the Residential branch, that scan can remove the Commercial marker and force-enable Apply after the calculator already disabled it for a different reason.

The authoritative `applyToJob()` remains fail-closed because it independently rechecks project blockers and hard BOM blockers. Therefore this is not a write-bypass. It is nevertheless a contradictory customer/operator-facing eligibility state and directly violates TASK_CURRENT:

```text
switching back to Residential restores normal eligible behavior only when the project is otherwise ready
```

Required correction:

- bridge must not own generic enabled state;
- on Commercial exit, remove only the Commercial-specific marker/decoration and delegate eligibility to calculator gating; or
- invoke/recompute authoritative calculator eligibility after removing the Commercial guard rather than setting `disabled=false` directly;
- add an executable regression for Commercial -> Residential while project is not-ready and while BOM has a hard financial/unresolved blocker.
