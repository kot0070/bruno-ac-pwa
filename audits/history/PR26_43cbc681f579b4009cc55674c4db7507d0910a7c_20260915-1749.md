## Executive_Verdict

**VERDICT: C — REJECT / REWORK REQUIRED.**

The exact PR26 HEAD is correctly resolved and the final diff/CI/PWA/code-registry evidence is largely coherent, but the live estimator/history integration contains multiple P1 blockers in the primary user path.

The central defect is a data-shape mismatch: `BrunoRoomEstimatorUX.getSnapshot()` returns a wrapper object shaped as `{ version, plan, result }`, while several downstream consumers treat that wrapper as if it were the normalized room plan itself. This breaks the live L0-L6 evaluation path, causes Confirm & Save to fail against the history-core plan validator, and prevents successful persisted room plans from being restored correctly after reload.

There is also an independent stale-ready defect: when a valid room plan becomes blocked, `room-estimator-live.js` stops invoking the authoritative Calculator but does not invalidate the previous BOM/pricing/Apply state. A prior ready BOM can therefore remain visually and operationally available after the current room plan is no longer valid.

No P0 financial corruption path was proven in this audit because live preview itself does not auto-Apply to Job. However, the core live estimator, history confirmation, persistence, and stale-state behavior are not acceptable for merge.

## Live_Level_Model

The engine defines the requested L0-L7 model:

```text
L0 Raw inputs
L1 Normalized building / room model
L2 Code / design requirements
L3 Calculated baseline
L4 Override / compliance
L5 BOM / components
L6 Catalog / pricing
L7 Confirmed snapshot / history
```

`earliestDirtyLevel()` itself passes the intended unit semantics exercised by the deterministic test:

- identical plan -> `null`;
- override-only change -> L4;
- room change -> L1.

However, the live integration does not provide the engine with the actual plan object.

`room-estimator-ux.js`:

```js
function getSnapshot(){
  ...
  return {version:E.VERSION,plan:plan,result:E.build(plan)}
}
```

`room-estimator-live.js` then does:

```js
var snap=ux.getSnapshot();
var dirty=E.earliestDirtyLevel(lastPlan,snap);
var result=E.build(snap);
```

`E.build()` expects a raw plan with top-level `building`, `rooms`, and `overrides`. The wrapper has those fields under `snap.plan`, not at top level. `normalizePlan(snap)` therefore falls back to default building data, an empty room list, and empty overrides.

Consequences:

- actual edited room/building data does not drive the live engine result;
- the level rail is not truthful for the user's current plan;
- override-only edits in the actual UI are not classified from the real override data;
- live readiness/blockers can diverge from the non-live room-estimator rendering;
- `calculatorInputs(result)` can push default-plan values into the Calculator preview.

**F01 — P1: live L0-L6 integration consumes the wrong object shape and evaluates a default plan instead of the current room plan.**

## Building_And_Room_Model

The core room model is structurally sound in `room-estimator-engine.js`:

- normalized building inputs;
- room types/counts/areas/conditioned state;
- per-room supply and branch run inputs;
- area reconciliation warning over 15%;
- no sqft-to-tonnage formula;
- planning supply defaults explicitly separate from code minimums;
- return grille count not inferred from sqft;
- unresolved new/replacement duct takeoff blocks when branch lengths are absent.

The deterministic engine tests cover these behaviors and passed in CI.

But persistence/reload is broken by a second wrapper mismatch.

`room-estimator-persistence.js` stores the full `getSnapshot()` wrapper under:

```text
state.acCalculator.roomEstimator
```

`room-estimator-preload.js` correctly reads `snap.plan.building` for early sqft/duct preload.

Then `room-estimator-ux.js` does:

```js
var saved=snapshotFromJob();
if(saved)return E.normalizePlan(saved);
```

The saved object is the wrapper, so it should use `saved.plan`. Instead `normalizePlan(saved)` again sees no top-level `building`, `rooms`, or `overrides` and reconstructs defaults.

The early preload does not repair this because `seedPlan()` returns immediately from the malformed normalization path rather than seeding from the DOM values it just preloaded.

**F03 — P1: successful room-estimator persistence cannot restore the saved room schedule/overrides/building plan after reload.**

## Confirmed_Snapshot_And_Active_Summary

The history core itself clones snapshots by value and assigns new IDs. The active-summary UI clearly labels the active historical record as a `frozen snapshot` and displays historical Customer Materials / Your Cost / Margin / Margin % separately from the live estimator's pricing area.

But `Confirm & Save Calculation` is broken by the same snapshot-shape mismatch.

`calculation-history-ux.js`:

```js
function roomPlan(){
  var ux=window.BrunoRoomEstimatorUX;
  return ux&&typeof ux.getSnapshot==='function'?ux.getSnapshot():null
}
```

That returns the wrapper `{version, plan, result}`.

`currentSnapshot()` places that wrapper into:

```js
snapshot.roomPlan = p
```

`calculation-history-core.js` validates `roomPlan` with:

```js
p.building && Array.isArray(p.rooms) && p.overrides
```

The wrapper has those fields under `p.plan`, so `saveSnapshot()` -> `normalizeSnapshot()` throws:

```text
invalid_room_plan
```

`saveConfirmed()` does not catch that exception.

Result: the primary Confirm & Save flow cannot create a valid history record from the actual room-estimator UX snapshot.

**F02 — P1: Confirm & Save is nonfunctional because history UX passes the wrapper object where history core requires the actual room plan.**

There is a second compliance semantic issue in `currentSnapshot()`:

```js
if((r.blockers||[]).length) ...
...
compliance:{ready:true,blockers:[],warnings:r.warnings||[],checks:r.checks||[]}
```

The engine always creates an `equipment-sizing` check with `status:'required-input'`, and may create additional required design checks, but these checks are not blockers. The history UX therefore hard-codes `compliance.ready:true` whenever only `r.blockers` is empty.

If F02 were corrected without correcting this semantic gate, a confirmed snapshot could state ready=true while preserving unresolved `required-input` checks.

**F05 — P1: confirmed-history compliance readiness is overclaimed; required-input checks are not considered before writing `compliance.ready:true`.**

Two additional non-blocking defects were identified:

**F06 — P2: duplicate provenance is computed but discarded by the UX.**

`duplicateForEdit()` returns `sourceCalculationId`, but `calculation-history-ux.js::duplicate()` only passes `d.roomPlan` to `loadPlan()`. A later confirmation does not inherit the source calculation identity.

**F07 — P2: import validation is structurally weak for historical financial completeness.**

`validateSnapshot()` primarily validates room-plan shape. `normalizePricing()` converts malformed/missing numeric values to null rather than rejecting the snapshot. A record with a valid room plan but incomplete/invalid historical pricing can therefore be admitted as an imported history record. It does not mutate Job pricing, so this is not classified as a P1 financial-integrity defect, but it does not fully satisfy the strong malformed-import acceptance expectation.

## Findings

### F01 — P1 — Live room estimator evaluates the wrong data shape

```yaml
files:
  - room-estimator-ux.js
  - room-estimator-live.js
  - room-estimator-engine.js
root_cause: getSnapshot returns {version,plan,result}; live code passes wrapper to engine as raw plan
impact:
  - actual room inputs do not drive live engine
  - level rail can be false
  - live blockers/compliance can diverge from actual plan
  - BOM/Catalog preview can be generated from default plan values
required_fix: pass snapshot.plan (or standardize getSnapshot API contract) and add executable integration coverage
```

### F02 — P1 — Confirm & Save cannot persist a normal UX calculation

```yaml
files:
  - room-estimator-ux.js
  - calculation-history-ux.js
  - calculation-history-core.js
root_cause: wrapper is assigned to snapshot.roomPlan but core requires top-level building/rooms/overrides
observed_failure: invalid_room_plan
impact:
  - no normal confirmed snapshot creation
  - active/history workflow cannot start from UI
required_fix: use ux.getSnapshot().plan consistently and add DOM/integration test for Confirm & Save
```

### F03 — P1 — Persisted room estimator does not restore rooms/overrides

```yaml
files:
  - room-estimator-persistence.js
  - room-estimator-preload.js
  - room-estimator-ux.js
root_cause: persisted wrapper is restored with E.normalizePlan(saved) instead of E.normalizePlan(saved.plan)
impact:
  - saved room rows and overrides are lost on reload
  - room-estimator persistence acceptance fails
required_fix: normalize saved.plan with backward-compatible shape handling and add reload round-trip test
```

### F04 — P1 — Blocked live edit leaves previous Calculator state ready/applyable

```yaml
files:
  - room-estimator-live.js
  - ac-calculator.js
  - ac-calculator-review-ux.js
root_cause: applyCalculatorPreview returns on blockers without invalidating prior BOM/pricing/review/Apply state
impact:
  - stale prior BOM and totals remain visible
  - existing Apply can still operate on prior in-memory scope/BOM
  - current room plan and applyable job material set can disagree
required_fix: fail closed when room preview becomes blocked; mark calculator stale/blocked and prevent Apply until a current valid Calculate completes
```

### F05 — P1 — History compliance readiness ignores required-input checks

```yaml
files:
  - room-estimator-engine.js
  - calculation-history-ux.js
root_cause: Confirm gate checks blockers only; snapshot hard-codes compliance.ready=true while required-input checks remain
impact: frozen history can materially misrepresent unresolved design/compliance state
required_fix: define authoritative confirmability semantics and derive ready from both blocker state and required checks
```

### F06 — P2 — Duplicate source identity is lost

```yaml
files:
  - calculation-history-core.js
  - calculation-history-ux.js
root_cause: duplicateForEdit returns sourceCalculationId but duplicate UX discards it
impact: reuse lineage is not preserved into the next confirmed snapshot
```

### F07 — P2 — Imported snapshot pricing completeness is not validated

```yaml
file: calculation-history-core.js

impact: malformed historical financial records can be imported, though they do not become current pricing authority or mutate Job data
```
