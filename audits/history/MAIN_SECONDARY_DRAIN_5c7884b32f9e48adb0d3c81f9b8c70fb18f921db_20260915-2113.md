## PRIOR P1 — RECHECK

### Blocking predicate

`secondary-drain-guard.js` computes the blocker from the live calculator DOM:

```text
installation scope active
AND overflowDamageRisk checked
AND overflowProtection in {pan-drain, overflow-drain}
AND secondaryDrainFt <= 0 / blank / invalid
```

The numeric normalization maps non-finite values to zero, so invalid/non-numeric values fail closed rather than silently passing.

### Required cases

Independent source inspection plus isolated execution of the exact guard logic produced:

```yaml
pan-drain + 0: BLOCKED
overflow-drain + blank: BLOCKED
overflow-drain + positive measured run: NOT_BLOCKED
pan-switch + 0: NOT_BLOCKED_BY_THIS_RULE
switch-only + 0: NOT_BLOCKED_BY_THIS_RULE
repair + installation scope disabled + pan-drain + 0: NOT_BLOCKED_BY_THIS_RULE
```

### Operator-visible state

When blocked, `render()`:

- sets `secondaryDrainFt[aria-invalid="true"]`;
- toggles the field parent `attention` class;
- sets `data-secondary-drain-blocked="1"` on Apply;
- sets `apply.disabled=true`;
- sets an explicit Apply title;
- replaces the Apply gate with a required-field blocker.

This closes the previous warning-only defect.

### Apply / Job mutation fail-closed

The guard registers a document-level capture-phase `click` listener. On `#apply`, it recomputes the blocker synchronously and, when blocked:

```text
preventDefault()
stopImmediatePropagation()
render(blocked state)
alert(operator)
```

The existing calculator registers its `applyToJob` handler on the Apply button in bubble/target processing. Therefore the capture listener executes first and blocks propagation before the Job mutation handler can run.

This is stronger than relying on the disabled property alone and protects against a stale button-state window between field input and deferred guard rendering.

## SWITCHING OVERFLOW METHOD

Changing from `pan-drain` / `overflow-drain` to `pan-switch` or `switch-only` removes only this drain-length requirement.

The calculator's normal `change` handler recalculates authoritative project/BOM/financial state. The drain guard then removes its own marker without enabling Apply itself. Therefore another active blocker continues to control the button.

## REPAIR MODE

`installationScopeActive()` returns false only when:

```text
jobKind === repair
AND includeRepairInstallScope is not checked
```

Thus repair/modification without installation-material scope does not receive a false secondary-drain blocker. If installation scope is explicitly re-enabled, the drain rule becomes applicable again.
