## 4. FINDINGS

### F01 — P1 — Employee FICA percentage is incorrectly applied to service-call revenue

**Observed production behavior (static source):**

`defaultState()` sets:

```text
taxesEnabled = true
revenueTaxPct = 7.65
```

`revenueTaxPct(call, settings)` returns that percentage for a service call, and `callNet()` computes:

```text
service_call_gross × (1 - 7.65%)
```

The UI labels the outputs `Tax est.` and `After tax`, and the settings control says `Apply tax estimate to service-call revenue`.

The explanatory note states the 7.65% default is employee FICA: 6.2% Social Security + 1.45% Medicare.

**Independent primary-source check (2026):**
- IRS Publication 15 (2026) states the Social Security rate is 6.2% each for employer and employee on taxable wages and Medicare is 1.45% each for employer and employee.
- IRS Topic 751 states the same rates and describes them as Social Security and Medicare withholding rates.
- Publication 15 also identifies a 2026 Social Security wage base of $184,500, no Medicare wage base, and separate 0.9% Additional Medicare Tax withholding above the applicable employer withholding threshold.

**Assessment:**

7.65% is a valid simple representation of the employee’s ordinary FICA share on covered wages (subject to wage-base/additional-Medicare details), but it is **not a general tax rate on business service-call revenue**. Applying it to customer gross revenue produces a financially misleading `After tax` amount even though the note says the model is simplified.

The helper take-home use of an employee-side 7.65% estimate is materially more defensible as an explicitly simplified payroll estimate. The service-call revenue calculation is the blocking defect.

**Required correction before acceptance:**
- remove FICA-derived 7.65% from service-call revenue taxation; or
- replace it with a clearly defined user-entered business tax/reserve model whose legal/accounting basis is not represented as employee FICA; and
- keep payroll FICA semantics separate from customer revenue/business-tax semantics.

### F02 — P1 — “Full app backup” omits the V2 Journal store

**Observed UI promise:**

`index.html` defines:

```text
Export app
Title: Full app backup: job + companies + workers + prefs
Import app
Title: Restore a full app backup JSON
```

**Observed export payload:**

`doExportApp()` serializes only:

```yaml
job: state
companies: profilesVault
uiPrefs: ui
catalogOpen: catOpen
```

There is no read/export of `bruno-ac-service-journal-v2`.

**Observed V2 journal persistence:**

`service-journal-ux.js` stores calls, crew, selected date/view and settings in a separate localStorage key:

```text
bruno-ac-service-journal-v2
```

**Impact:**

A user can create service calls, helper payroll entries, and tax settings, perform a product-labeled full-app backup, restore that backup on another installation/device or after storage loss, and discover the Journal data is absent. This is a direct mismatch between the backup promise and recoverable data.

**Required correction before acceptance:**
- include the full V2 Journal payload in Export App and Import App;
- version/validate the imported journal payload;
- preserve non-destructive migration rules;
- add executable export→clear→import→journal-equivalence coverage.
