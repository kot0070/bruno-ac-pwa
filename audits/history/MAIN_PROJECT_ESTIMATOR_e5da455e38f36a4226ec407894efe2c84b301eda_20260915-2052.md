## FINDING

### F01 — P1 — Full technical calculator permits Apply with a missing field-required secondary/overflow drain length

The second-stage technical calculator offers overflow-protection methods including:

```text
pan-drain
overflow-drain
```

For both methods, the engine requires an actual separate secondary/overflow run to a conspicuous point when generating the required drain material. But when `secondaryDrainFt` is `0`, the engine does not create the required drain row and records only a warning:

```text
Secondary overflow-drain method selected but secondary drain length is 0 ft. Enter the actual field run before pricing.
```

or:

```text
Separate overflow-drain method selected but secondary drain length is 0 ft. Enter the actual field run before pricing.
```

The authoritative Apply gate does not treat scope warnings as hard blockers. `hardBlockingRows()` blocks only selected BOM rows that are unresolved, financially invalid, or have invalid Customer/Your pricing. A missing required drain run produces no blocking BOM row, so once the remaining selected BOM is otherwise resolvable and financially valid, Apply can remain enabled and `applyToJob()` can persist the incomplete material snapshot.

This is a direct mismatch with TASK_CURRENT requirements:

```text
field-required lengths/values remain required rather than inferred
live overrides and fail-closed Apply
```

It is also inconsistent with the engine's own code-check semantics: when overflow can damage building components, the UI declares an allowed protection method required, but one of the required field quantities for the selected method is not enforced before Apply.

Current Texas ACR context also makes the distinction material. TDLR adopted the 2024 IRC/IMC/IFGC/UMC baseline effective September 1, 2026, while local adopted municipal code/AHJ requirements continue to control where applicable. Primary TDLR rulemaking source: https://www.tdlr.texas.gov/news/rulemaking/2026/08/31/commission-adopts-rules-11/

Required correction:

- represent `secondaryDrainFt` as an authoritative required-input blocker whenever the selected overflow method requires a separate drain run;
- prevent Apply until a positive measured run is supplied, or until the operator selects a different valid overflow-protection method;
- do not satisfy the requirement by inventing/defaulting a run length;
- add executable regression coverage for at least `pan-drain + 0 ft` and `overflow-drain + 0 ft`, proving Apply remains disabled / authoritative Apply rejects before Job mutation;
- keep the existing current-Catalog and financial blockers in the same combined gate.

Severity is P1 because this is a fail-closed compliance/material-scope bypass in the accepted production calculator path, not a cosmetic warning defect.
