## 5. PRIOR F02 — FULL APP BACKUP

### What is fixed

`app-backup-bridge.js` collects every localStorage key beginning with `bruno-ac-`, including `bruno-ac-service-journal-v2`, and excludes unrelated keys.

`buildBackup()` creates a versioned `bruno-ac-full-app-backup` v2 payload. `restoreBackup()` writes only `bruno-ac-*` keys.

`tests/app-backup-bridge.test.js` verifies:
- Journal is exported;
- another Bruno store is exported;
- unrelated `other-app` is excluded;
- restore into new/empty storage preserves Journal string exactly;
- non-Bruno key in backup is rejected.

CI executes this test successfully.

Legacy UI handlers are intercepted in normal main-page use by the dynamically loaded backup bridge, which installs capture listeners on `btn-export-app`, `help-export-app`, and `btn-import-app` and calls `stopImmediatePropagation()` before invoking the new bridge action. This is **STATIC PASS**; actual browser event dispatch was not executed.

### F02 — P1 — Journal payload is not actually content-validated before restore

`validateBackup()` validates only:
- top-level product/type/version;
- `storage` is an object;
- each key starts with `bruno-ac-`;
- each value is a string.

It does **not** parse `bruno-ac-service-journal-v2`, verify JSON validity, verify `schemaVersion`, or verify the expected calls/crew/settings shape. Therefore this payload is accepted:

```json
{
  "product": "bruno-ac",
  "type": "bruno-ac-full-app-backup",
  "version": 2,
  "storage": {
    "bruno-ac-service-journal-v2": "not-json"
  }
}
```

The bridge writes the malformed Journal string. On reload, Journal `load()` catches parse failure and falls back to legacy/default state, so the import can report success even though the Journal payload was not restored as usable Journal data.

The previous audit explicitly required version/validation of the imported Journal payload. Current test coverage does not include malformed Journal JSON/schema/version.

**Required correction:** validate the Journal value before any writes (JSON parse + supported schema + minimally valid shape), fail closed on invalid payload, and add a negative executable fixture plus export->empty storage->import->semantic Journal equality test.

## 6. F03 — P1 — COMMERCIAL MODE CAN BYPASS FAIL-CLOSED APPLY THROUGH STANDALONE CALCULATOR

Embedded Calculator correctly stores project context in `bruno-ac-project-context-v1`, shows a commercial warning, and `project-mode-bridge.js` disables `#apply` in the iframe when type is Commercial.

However `navigation-v2.js` also exposes `Open standalone` and navigates directly to `./ac-calculator.html`.

`ac-calculator.html` loads:
- `ac-calculator-engine.js`
- `ac-calculator.js`
- `ac-calculator-ux.js`
- `ac-calculator-review-ux.js`

It does **not** load `project-mode-bridge.js`. `ac-calculator.js` does not read `bruno-ac-project-context-v1`; `loadState()` explicitly enables `#apply`, and `applyToJob()` can write the generated BOM into `bruno-ac-v1`.

Result: a user can select Commercial, click `Open standalone`, then apply the residential-oriented calculator BOM to Job. This violates the explicit fail-closed acceptance boundary.

**Required correction:** enforce project-mode gating inside the calculator/apply path itself (not only iframe decoration), including standalone mode. Prefer a single authoritative guard in `applyToJob()` or equivalent core integration boundary.

## 7. F04 — P1 — MONTH / QUARTER PREV-NEXT NAVIGATION USES FIXED DAYS AND CAN SKIP ARCHIVE PERIODS

`service-journal-ux.js` uses:

```text
rangeStep(): day=1, week=7, month=31, quarter=92
Prev/Next: shiftDate(selectedDate, +/-rangeStep())
```

This is not calendar-safe.

Representative failures:
- `2026-01-31 + 31 days = 2026-03-03`: Month Next skips February.
- `2026-12-31 + 92 days = 2027-04-02`: Quarter Next lands in Q2 and skips Q1 2027.

`rangeBounds()` itself is correct once a date is selected, but the navigation control can skip the next archive period.

Current tests only cover representative `rangeBounds()` values; they do not test Month/Quarter Prev/Next transitions.

**Required correction:** shift by calendar month/quarter while preserving/clamping day safely, or move to period starts before adding one month/three months. Add end-of-month/year executable fixtures.

## 8. F05 — P1 — MULTIPLE-HELPER PAYROLL WAGE BASES USE MUTABLE NAME AS EMPLOYEE IDENTITY

`payrollLedger()` derives YTD key as:

```text
year + '|' + lowercased trimmed helper name
```

Each crew row has a unique entry `id`, but there is no stable employee/personnel identifier for cross-day payroll accumulation.

Consequences:
- two different workers named `Helper` are treated as one employee for SS/TWC/FUTA wage bases;
- the Add Helper modal defaults every new worker name to `Helper`, making collision plausible;
- renaming the same worker creates a new YTD identity and resets their wage-base progress;
- two people with the same real name also collide.

This matters because FUTA/TWC/SS limits are **per employee**. Example: if two distinct helpers each earn $9,000 but both are stored as `Helper`, the second helper can receive little or no TWC/FUTA employer tax estimate after the pooled key reaches the first worker's wage bases, understating employer crew cost.

**Required correction:** tie journal crew rows to a stable worker/personnel ID (or create a stable Journal worker ID) and use `year + workerId` for wage-base ledgers. Name should remain display data only. Add multiple-helper/same-name and rename regression fixtures.
